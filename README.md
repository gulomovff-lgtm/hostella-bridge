# Hosti Bridge — мост e-mehmon для Hosti Cloud

Программа в трее на компьютере филиала. Касса Hosti Cloud работает в браузере
и не может открыть `emehmon.uz`, чтобы заполнить там форму, — это принцип
безопасности веба. Поэтому касса ставит **задачу** в Firestore, а мост на
стойке её забирает, выполняет в скрытом окне портала и записывает итог.
Кассир видит результат в карточке гостя.

Контракт очереди (типы задач, статусы, форма результата) живёт в репозитории
кассы: `hostella-cloud/docs/МОСТ.md`. Скрипты портала — боевые, из Hostella
(`electron/emehmonAutofill.js`), без изменений.

## Что делает

| Задача | Что происходит в портале | Итог кассе |
|---|---|---|
| `probe` | первый шаг мастера прибытия: госбаза находит гостя, вторая вкладка отдаёт дату и № КПП, третья — до «Сохранить» | `valid` + дамп вкладок / `not_found` |
| `arrival` | весь мастер прибытия; с `gateStays` — остановка перед «Сохранить» и список прошлых проживаний | `done` / `needs_decision` / … |
| `departure` | убытие гостя из `/listok`; лист убытия снимается в PDF и кладётся в хранилище кассы (`result.sheet`) | `done` / `submitted` / … |
| `sheet` | лист убытия заново со страницы выехавших `/listokout` — гостю, выведенному раньше или без листа | `done` / `not_found` / … |
| `check` | есть ли гость в активном списке | `present` / `absent` |
| `list` | весь активный список для сверки | `ok` + `rows` |
| `tursbor` | отчёт туристического сбора за период | `ok` + `data` |
| `recalc` | пересчёт сумм в листках | `done` / `not_found` (ни одна строка не совпала) |

Исход мастера (`done`, `needs_decision`, `valid`, `not_found`, …) пишется как
`done` с `result.status`; временное (`need_login`, портал не ответил, комнату
не нашли) — как `failed` с `error.code`, чтобы касса могла повторить. Строки
таблиц в дампах — плоские (`ячейка | ячейка`): Firestore не принимает массив
в массиве.

Задачу берут с арендой на две минуты и продлевают, пока мастер работает. Если
мост упал посреди задачи, её перехватит любой мост филиала, как только аренда
истечёт (с 0.3.2); когда попытки кончились — `failed/stale`, и решает касса.
Итог не перетирает отмену: перед записью задача перечитывается.

## Установка на компьютере филиала

1. Собрать установщик: `npm install`, затем `npm run dist` → `release/Hosti Bridge Setup x.y.z.exe`.
2. Установить на компьютер стойки (тот, где уже входят в e-mehmon).
3. В кассе (владелец или администратор): Настройки → Мост e-mehmon →
   подтвердить согласие → «Подключить мост» → код на 15 минут.
4. В окне моста ввести код → «Подключить». Мост получает учётку с ролью
   `bridge` и доступом только к очереди своего филиала; пароль ему не выдаётся.
5. Вписать логин и пароль портала e-mehmon филиала → «Сохранить» → «Войти
   в e-mehmon…»: откроется окно портала с подставленными логином и паролем,
   капчу и «Войти» нажимает человек. Сессия портала живёт долго.
6. Мост сворачивается в трей и запускается вместе с Windows. Касса видит его
   «в сети», пока heartbeat моложе 90 секунд.
7. Обновляется сам с GitHub Releases (`gulomovff-lgtm/hostella-bridge`): тихо
   скачивает и ставит, когда очередь свободна и никто не вводит капчу.

Пароль от e-mehmon хранится только на этом компьютере, зашифрованным
средствами Windows (DPAPI). В Firestore его нет ни в каком виде. Refresh
token моста — там же.

## Когда мост просит внимания

* **Нужен вход в e-mehmon.** Портал разлогинил сессию: мост показывает окно
  входа и уведомление в трее, очередь стоит до входа. Задача, на которой это
  выяснилось, уходит кассе как `failed / need_login` — кассир видит причину.
* **Отключён администратором.** В кассе нажали «Отключить мост»: учётка
  выключена, мост это распознаёт и просит новый код.
* **Нет связи.** Heartbeat не проходит — мост пробует снова каждую минуту;
  касса через 20 минут поднимет полосу над кассой и напишет владельцу.

## Разработка

```
npm install
npm test                      # чистые модули: кодек REST, исходы, очередь, сессия, хранилище
npm start                     # Electron, рабочий проект
npm run dist                  # установщик в release/, без публикации
npm run release               # установщик + черновик релиза на GitHub через gh (scripts/publish.js:
                              # exe под именем из latest.yml, сам latest.yml и blockmap — одним черновиком);
                              # черновик публикуют: gh release edit vX.Y.Z --repo gulomovff-lgtm/hostella-bridge --draft=false --latest
npm run start:demo            # Electron против эмуляторов hostella-cloud
npm run core:demo -- pair <код>            # ядро без Electron: подключение
npm run core:demo -- run [scenarios.json]  # ядро без Electron: очередь со stub-порталом
```

`scripts/core-run.mjs` гоняет всё, кроме самого портала, на эмуляторах кассы
(`npm run emulators` в `hostella-cloud`): подключение кодом, heartbeat,
взятие задачи с предусловием, запись итога. Stub-портал отвечает по файлу
сценариев (`scripts/scenarios.example.json`): по типу задачи, по гостю,
`whenGate` / `whenForce` — как боевые скрипты при `gateStays` / `force`.

Структура:

```
main.js              Electron: трей, окно настроек, сборка частей
src/config.js        профили prod/demo, интервалы
src/firebaseRest.js  Firebase без SDK: токены, Firestore REST, callable
src/auth.js          код подключения → сессия моста, обновление токена
src/queue.js         очередь: claim с предусловием, аренда, итог, пауза
src/outcome.js       вывод скрипта → done/failed, плоские дампы
src/portal.js        окно портала, боевые скрипты, вход кассира
src/store.js         локальное хранилище, секреты под DPAPI
electron/emehmonAutofill.js   копия из Hostella
ui/                  окно настроек (без фреймворков)
```

Почему REST, а не Firebase SDK: у SDK нет входа по refresh token, а мост
живёт неделями без человека и после перезапуска не должен просить новый код.

## Защита данных

Через мост проходят паспортные данные гостей, поэтому:

- все адреса — только https, TLS не ниже 1.2 (и в Node, и в Chromium); боевой
  профиль с любым http-адресом не стартует (`src/config.js`, `assertSecure`);
- ошибка сертификата — обрыв соединения, «продолжить» некому;
- задачи очереди живут в памяти и на диск не пишутся; номера паспортов
  вырезаются из журнала (`src/redact.js`);
- пароль портала и ключ моста — под DPAPI пользователя Windows (`src/store.js`);
- портал открывается в изолированной сессии филиала: уход с emehmon.uz,
  запросы по http и запросы разрешений заблокированы (`src/portal.js`).

Окно «Защита данных гостей» показывает эти факты по состоянию моста, а не
по обещаниям: список хостов и признак «только https» берутся из профиля.

## Подпись установщика

Сейчас установщик и обновления **не подписаны**: сертификата подписи кода
нет, а строка electron-builder «signing with signtool.exe» без него ничего
не подписывает (проверка — `Get-AuthenticodeSignature` по exe: NotSigned).
Без подписи `electron-updater` не проверяет издателя обновления, и подмена
релиза в репозитории означала бы выполнение чужого кода на компьютерах
кассиров. Закрыть это может только владелец — сертификатом (OV/EV либо
Azure Trusted Signing).

Когда сертификат появится:

1. задать `CSC_LINK` (путь или base64 .pfx) и `CSC_KEY_PASSWORD` в окружении
   сборки — electron-builder подпишет exe сам, конфиг менять не нужно;
2. добавить в `package.json` → `build.win.publisherName` имя издателя ровно
   как в сертификате — с этого момента `electron-updater` отвергает
   неподписанные и чужие обновления (поэтому раньше времени ставить нельзя:
   нынешние неподписанные сборки перестали бы обновляться);
3. `scripts/publish.js` при заданном `CSC_LINK` отказывается публиковать
   неподписанный exe — сборка без подписи не уедет молча.
